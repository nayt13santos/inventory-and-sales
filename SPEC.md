# Octogo Takoyaki — Daily Tracker (PWA + Google Apps Script + Google Sheets)

One system, three parts:
1. **Google Sheet** = database (free, owner-readable, no vendor lock-in).
2. **Apps Script Web App** = free JSON API bound to that sheet (deployed by owner, "execute as me", "anyone with link").
3. **PWA** = phone-installable app (static hosting), offline-first, syncs when online.

Users: **Mama** (daily entry at closing time), **Nayt** (dashboard + bi-monthly cutoff note).
Locale: Philippines. Timezone **Asia/Manila** everywhere. Currency PHP. Dates are plain strings `yyyy-MM-dd` end-to-end (never Date objects in sheet cells — write as strings with a leading `'` not needed if column formatted as plain text; Apps Script must set number format `@` on date columns).

## Business rules (verified against owner's real cutoff notes)

- Cutoff periods: **1–15** and **16–end of month**.
- Daily sales are computed from **container counts**: start-of-day (SOD) vs end-of-day (EOD) per box size. Sold = SOD − EOD. Sold then splits into four buckets — Cheese, GCash, GCash Cheese, and plain regular cash as the remainder (see the DailyCounts section).
- Current prices (seed data; editable in sheet `Prices` tab):
  - Octobits (regular): 4pcs ₱50, 6pcs ₱65, 10pcs ₱105
  - Chizubits (cheese): 4pcs ₱60, 6pcs ₱80, 10pcs ₱125
  - No drinks SKU (owner sells takoyaki only). To add one later, append a Prices row with `group=simple`.
- Custom orders: free peso amount + optional note per day.
- **GCash is computed**, not typed: it is the sum of the per-sku GCash buckets plus `custom_gcash`. **Cash = Total − GCash** still holds. The receipt displays the computed GCash so it can be reconciled against GCash history.
- **Split is an ENTERED amount, not the residual** (owner, 2026-08-03). Default `split_default` = ₱3,000 (₱1,500 each), editable per cutoff. `per_partner = split / 2`.
- Identity is therefore `Total = Cash + GCash` and `Total = Mama + Split + Supplies + Octopus + Salary + Other payments + Electric + Remaining`, where **Remaining is the residual** — what is left in the business after everything, and the figure backlog payments are funded from. Remaining may be negative (a short cutoff); show it, never clamp it.
- **Daily salary** ₱200 (`daily_salary`, Settings) is added automatically for every day NOT marked closed, snapshotted onto the day when it is saved so a later rate change never rewrites history. Editable per day for a half day. Subject to change once the owner finishes costing.
- **Mama** ₱500 per cutoff is her **share** (she is a third person — not the partner the Split is divided with) and **Electric bill** ₱500 are per-cutoff amounts logged as expenses, each offered as a one-tap chip on the Cutoff screen.
- **Octopus** is its own expense category (bulk purchase, paid per cutoff — kept separate from Supplies by owner's explicit request).
- **Backlog payments**: owner maintains a list of debts/obligations ("backlogs"), each with a total amount and running balance; he pays variable amounts per cutoff depending on excess. These payments + misc = the note's "Other payments" line.

### Cutoff note format (must match EXACTLY, including blank line placement; numbers use thousands separators, no ₱ sign, no decimals for whole numbers)

```
Tañong: July 1 - 15 Breakdown

Total - 11,857

Cash - 10,530
GCash - 1,327

Mama - 500
Split - 3,000(1,500 each)
Supplies - 5,440
Octopus - 
Salary - 3,000
Other payments - 1,417
Electric bill - 500

Short - 2,000
```

Rules, all load-bearing:
- When a category is zero, keep the line with a **blank value after "- "** — exactly as `Octopus - ` above (note the trailing space). Branch name from Settings.
- `Total`, `Cash` and `GCash` always print a number (`0` when empty); only the seven expense/share categories blank at zero.
- The final line is the residual and its LABEL carries the sign, so a note never reads `- -2,000`:
  `Remaining - 1,000` when ≥ 0, `Short - 2,000` when negative. It always prints a number.
- `Salary` was added 2026-08-03 and the residual line with it. The old ten-line note is no longer canonical; this is.

## Google Sheet schema (created by `setupSheet()` in Apps Script — flat tables, row 1 = headers, NO merged cells)

Tab **Settings** (key | value):
- `token` — API shared secret (random 32 chars, generated by setup)
- `branch` — "Tañong"
- `mama_per_cutoff` — 500
- `electric_per_cutoff` — 500
- `partners` — "Nayt, Partner" (display only)
- `staff` — "Mama" (comma-separated list for staff picker)
- `daily_salary` — 200 (added to every non-closed day; snapshotted per day at save)
- `split_default` — 3000 (pre-fills the Cutoff screen's editable Split)

Tab **Prices** (sku | label | group | size | price | cheese_price | active | **in_cutoff**):
- `box4` | Box 4 | box | 4 | 50 | 60 | TRUE | TRUE
- `box6` | Box 6 | box | 6 | 65 | 80 | TRUE | TRUE
- `box10` | Box 10 | box | 10 | 105 | 125 | TRUE | TRUE
- `nori` | Nori | simple | | 25 | | TRUE | **FALSE**

**`in_cutoff` = FALSE means "sell it, count it, but keep its money out of every cutoff figure"** (owner, 2026-08-04: nori is his own line of business — "it must not be added to the bi-monthly cutoff, just show the total per cutoff, and I'll exclude it on my own").

(`group=box` → SOD/EOD + cheese split; `group=simple` → SOD/EOD only, single price. Nori is `simple`: start/end counts, one price, no cheese and no GCash split.)

> **A BLANK `in_cutoff` MUST read TRUE.** After migration every existing Prices row has an empty cell in that column; if blank were read as FALSE, every takoyaki sku would silently drop out of the cutoff and the note would collapse to almost nothing. Blank = counts in. The same rule applies to an unrecognised value — anything that is not explicitly false-y counts in, because the failure mode of guessing wrong is deleting money from the note.

> **The flag is SNAPSHOTTED onto each DailyCounts row at save time**, exactly as prices are, and history is classified by that snapshot — never by the current Prices flag. Otherwise flipping "counts in the cutoff" in Maintenance silently restates money that was already saved, in both directions: a past ₱300 of nori would either vanish from the excluded block or reappear inside a total it was never part of. A BLANK snapshot on a count row reads TRUE (v2.5.0): a legacy row's money provably reached `total` when it was saved, so classifying it by the CURRENT flag double-stated migrated history the moment a sku was excluded. Blank = it counted.

> **An excluded sku must be `group=simple`.** Keeping money out of the cutoff means it is one plain quantity × one price — no cheese variant and no cash/GCash split. `savePrices` and `saveDay` both refuse `in_cutoff=FALSE` on a `group=box` sku, and refuse a non-zero cheese or GCash bucket on any excluded sku, naming the item in plain English. Without that rule the UI hides the cheese steppers while the payload still carries cheese quantities, so the phone and the sheet disagree about what was sold.

Tab **DailyLog** (date | closed | staff | gcash | total | cash | custom_amount | notes | entry_id | updated_at | **custom_gcash** | **salary** | **excluded_total**) — one row per date, upsert by date. `gcash` is now **computed** (see below), not typed. `custom_gcash` = how much of `custom_amount` was paid by GCash. `salary` = that day's wage, snapshotted from Settings at save time (0 on a closed day); a blank on a pre-existing non-closed row counts at the current `daily_salary`. `excluded_total` = that day's money from `in_cutoff=FALSE` skus, stored separately and **never** part of `total`, `cash` or `gcash`.

Tab **DailyCounts** (date | sku | sod | eod | sold | cheese_qty | regular_qty | amount | entry_id | **gcash_qty** | **gcash_cheese_qty** | **gcash_amount** | **in_cutoff** | **price** | **cheese_price** | **custom_qty**) — N rows per date, rewritten on day upsert, computed **server-side**; `price`/`cheese_price` are the v2.5.0 per-row price snapshots the money was computed from, and `custom_qty` (v2.7.0, the last column) is how many of that sku's sold boxes a special order drew — priced at nothing, because the order's typed amount is its whole value.

**Four payment/variant buckets per sku** (mirrors the owner's own Sales Calculator: Cheese / GCash / GCash Cheese / Regular). They are mutually exclusive and must sum to `sold`:

| column | meaning | entered? |
| --- | --- | --- |
| `cheese_qty` | cheese, paid **cash** | yes |
| `gcash_qty` | regular, paid **GCash** | yes |
| `gcash_cheese_qty` | cheese, paid **GCash** | yes |
| `regular_qty` | regular, paid cash | **derived** = sold − the three above |

```
amount       = (regular_qty + gcash_qty) * price + (cheese_qty + gcash_cheese_qty) * cheese_price
gcash_amount = gcash_qty * price + gcash_cheese_qty * cheese_price
```

**Snapshots travel with the FIRST save too (v2.5.1).** A saveDay count may carry the `price`, `cheesePrice` and `inCutoff` the phone DISPLAYED when the night was entered; the server uses them for a sku's first row on that date, so a save queued offline lands at the money the receipt and the tin showed — never at whatever the prices happen to be when it finally syncs. On a RE-save, the stored per-date snapshots win (payload values fill only skus new to that date). Classification on re-save uses the stored `in_cutoff` snapshot for the same reason: a Maintenance flip must never move an already-saved day's money between the cutoff and the excluded block — the Sales screen, the Cutoff screen and the sheet must tell one story.

Day roll-up counts **only `in_cutoff` skus**: `total = Σ amount (in_cutoff only) + custom_amount`, `gcash = Σ gcash_amount (in_cutoff only) + custom_gcash`, `cash = total − gcash`, and `excluded_total = Σ amount (in_cutoff=FALSE)` kept entirely apart. So **Cash = Total − GCash still holds**, but GCash is now derived from what was actually entered instead of read off the GCash app. The receipt shows the computed GCash so it can still be reconciled against GCash history.

`group=simple` skus have no cheese: `cheese_qty` and `gcash_cheese_qty` must be 0; only `gcash_qty` splits payment.

Tabs **SupplyItems** / **DailySupplies** — **RETIRED 2026-08-03.** The owner judged the nightly "supplies bought today" card redundant with the Expenses tab, so the card is gone, `saveDay` no longer writes these tabs, and the cutoff no longer reads them: **`Supplies` on the note is now Expenses(category=Supplies) alone.** The tabs are left in place (never deleted — that is the migration rule) but are dead. Anything an early user typed there stops counting; there was no such data when this changed.

Tab **StockItems** (product | unit | active | sort) — the unit is the thing you OPEN, not a weight: Takoyaki Flour (pack), Takoyaki Sauce (gallon), Japanese Mayo (pack), Bonito (pack), Aonori (pack), Togarashi (pack).

Tab **StockUsage** (date | product | qty | entry_id | updated_at) — **whole units opened that day, counted like the boxes** (owner, 2026-08-03: "if a gallon of sauce is opened, it's considered used in that day"). Integers only — never fractional weights, never a running estimate. Only non-zero rows. **Never money**: it touches no total and no note line; it drives on-hand and the reorder warning.

### v2.7.5 — the sheet protects itself, and can be audited

**Weekly backups live in their OWN Apps Script project** (`standalone-scripts/Backups.gs`), never in the sheet's bound script. This separation is load-bearing, not tidiness: Apps Script grants permissions **per project**, and the bound project is what serves the phones. Copying files needs Drive permission and a schedule needs trigger permission; adding either to the bound project grows the permission set the LIVE web app runs under, and until the owner re-authorises it in the editor an ordinary night's save can fail. `run-tests.js` therefore asserts Code.gs contains no `DriveApp`, `ScriptApp`, `MailApp`, `GmailApp` or `UrlFetchApp` at all — a permanent fence. The standalone project reaches the sheet as a **Drive file** — `DriveApp.getFileById(SPREADSHEET_ID)`, whose `getName()` is all it needs, so it never asks for permission to read spreadsheet content at all — pins its weekly hour with `.inTimezone(TZ)` (a fresh project inherits whatever zone Google gives it, rarely Manila), `Logger.log`s its result because the editor never displays a return value, refuses to arm while that id is still the placeholder, replaces its own trigger rather than stacking a second, makes at most one dated copy per day, and trashes copies beyond the newest 8 (Drive's trash is the second net).

**`sheetCheck`** (action, pure read, no lock — it calls only read paths) audits the whole sheet for the damage a hand-edit can do and answers `{findings:[sentence…], checked_rows}`; the phone surfaces it as **More → "Check the sheet"** and escapes every finding exactly once (they carry sheet data). It reports: **a date cell that is not a date** (v2.7.5 — `asDateStr` normalises the shapes it knows and returns anything else verbatim, so a hand-retyped `28-07-2026` survives into every reader AS a date and, because period filters are string compares, that row's money falls outside every cutoff forever with no total complaining; checked across all eight date-bearing tabs); stray duplicate rows in any upsert-keyed tab (readers keep the FIRST, so a duplicate is data the owner sees but the app ignores); an active price of 0 (or a box's cheese price of 0); an excluded `group=box` sku; expense categories the note does not know, backlog payments pointing at no Backlogs row, and non-positive amounts; DailyCounts rows whose day is missing from DailyLog (a half-died save, since DailyLog is written LAST); stock rows naming products the StockItems list does not have; and a DailyLog row whose stored Total ≠ Cash + GCash. Finding nothing is the expected answer and is SAID, not left blank.

### v2.7.6 — the Cutoff screen says what is MISSING, not just what is there

A note is built from the days that exist, so an unlogged night reads as a lean night rather than as absent work: the owner's own Aug 7–15 (nine days, no entry at all) made a fortnight preview say **Short** with nothing on screen explaining why. The Cutoff screen therefore names the two silences before the figures:

- **`missingDaysInPeriod(per)`** — dates in the period with no DailyLog row at all, each offered as **"Enter it"** (opens that date on the Sales screen) or **"Was closed"** (queues a closed day for it, after a confirm). A day marked **closed is entered** — "the stall was dark" is an answer, not a gap. It never looks past **today**, and returns nothing at all when `previewIncomplete(per)` — outside the snapshot window the phone would be inventing gaps from history it does not hold. It is **advisory and never blocks the note**: an unlogged day may be perfectly deliberate, which is exactly why it is said rather than enforced.
- **A period with no purchases at all** gets one quiet line, because "no expenses" and "expenses not yet entered" look identical in a total.

`addDays` (parts-based, so month/year/leap rolls cannot drift with a timezone) does the walk.

### v2.8.0 — "What it costs": the costing the owner asked for, computed by the app

The owner's question (2026-08-19): *"Costing of the current setup, how much should the price be in correlation with the daily expenses."* Answered by hand once from nine nights; this makes it permanent and self-maintaining, so every cutoff answers it from what was actually logged. **Baseline starts 2026-08-16** — earlier days are incomplete by the owner's own account ("the user is just getting around for it").

**Two cost sources, never mixed** — this is the load-bearing rule:
- **Consumption** for the things he buys in bulk and opens: `Σ StockUsage.qty × StockItems.unit_cost` (new append-only column, seeded with his figures: Takoyaki Flour ₱120, Takoyaki Sauce ₱490, Japanese Mayo ₱300, Bonito ₱900, Aonori ₱550, Togarashi ₱320 — each *per the unit it is counted in*).
- **Money out** for everything else that becomes a ball: `Expenses` in category `Supplies` or `Octopus`, **minus every row this ledger already prices per unit**. The mapping is **DECLARED, not guessed** — Settings **`costed_buckets`** (seeded "Flour, Sauce, Mayo, Bonito, Aonori, Togarashi, Box") lists the expense-form bucket names whose money is counted per unit elsewhere. A row is set aside when (1) its item is one of those buckets, (2) its item IS a tracked product name (hand-typed), or (3) it carries a legacy `stock_product`. The set-aside total ships as `variable.counted_per_unit` so the subtraction is visible rather than a figure that silently disagrees with the Expenses screen.
  > **Why declared and not inferred.** The first version matched an expense's `item` against StockItems product names only — but the expense form writes BUCKET names ("Flour", "Box") and no bucket equals a product ("Takoyaki Flour"), so the guard could never fire on anything the app itself wrote: flour counted twice (paid AND opened), boxes twice (the Box bucket AND boxes sold × `box_cost`), reading ~30–60% too dear. Inference was rejected because guessing wrong in the other direction removes real money from the cost, and an under-stated cost is what makes a price look safe to cut.
- **Containers**: `Σ per-sku boxes sold × Prices.box_cost` (new append-only column; seeded Box 4 ₱0.375, Box 6 ₱3.00, Box 10 ₱4.60 = his bundle prices ÷ bundle counts; a `simple` sku may be 0).
- **Fixed, not per ball**: each open day's snapshotted `salary`, plus `mama_per_cutoff` + `electric_per_cutoff` spread across the period's open days.

**CAVEATS, and the one thing they switch off.** The figures are only as complete as the logging, and an **under-stated** cost is the dangerous direction — it makes a price look safe to cut. Proven on the owner's real Aug 16–31: with no purchases logged yet, cost per ball read ₱1.57 instead of ~₱5.80 and the targets advised dropping Box 10 from ₱105 to ₱83. So `costing` returns **`caveats:[sentence…]`**, of two kinds:
- **Cost is a floor** (`no purchases logged in the period`; a used product with no `unit_cost`; or — v2.9.2 — **money set aside on a promise that was not kept**: paid on a `costed_buckets` row for STOCK while nothing was logged as opened in the period, so that money is counted nowhere at all. The set-aside ships split as `counted_as_stock` / `counted_as_boxes`, because a CONTAINER promise keeps itself the moment a box sells while a stock promise needs an opening logged, and the old single floor gate could not see the difference: one octopus purchase made `moneyCost` positive and stood the whole warning down) → biases advice DOWN → **`targets` is emptied**. Advice computed from data known to be incomplete is worse than no advice, and the screen says so where the table would have been.
- **Thin period** (days with nothing entered) → the per-cutoff shares land on fewer nights, biasing cost per night UP → conservative, so the advice **stays** with its warning attached.
Blank days are counted only up to **yesterday**: tonight has not happened at nine in the morning, and calling that a gap would cry wolf every single day. The screen renders the caveats **above** every figure they qualify, and its wording follows whether the advice is off or merely cautious.

New action **`costing`** payload `{start, end, targetPerDay?}` → `{days_open, balls, revenue, caveats, variable:{stock, money, boxes, per_ball}, fixed:{salary, shares, per_day}, per_sku:[{sku, label, sold, price, cost_per_box, margin_per_box, margin_per_ball}], break_even_balls, per_day:{revenue, cost, left}, targets:[{per_day, prices:[{sku, price}]}], unpriced:[…]}`. Pure read, same 1–15 / 16–end periods as the note, and it **never touches the note or any cutoff figure** — costing is management information, not money that has moved.

Honesty rules, all load-bearing:
- A tracked product with **no `unit_cost`** is listed in `unpriced` and its consumption is left OUT of the total rather than silently costed at 0 — a cost that is quietly too low is worse than one that is visibly absent.
- **Balls** come from the sold counts × each sku's `size` (a `simple` sku has no size and contributes none), and excluded skus (nori) are out of both revenue and cost — its money was never in the cutoff either.
- Zero balls or zero open days ⇒ every per-ball figure is `null`, never a division by zero dressed as ₱0.
- The screen states its window and says plainly which figures are *money paid this period* rather than *consumed this period*, because over a short window those differ.
- **Target prices are advice, never applied**: the action returns what each price *would* need to be for a chosen nightly take; nothing writes to Prices. The factor scales the **scalable** takings only — revenue less the typed custom-order money, which no menu price can move (`custom_orders_held` says when that applied) — and is applied to each sku's **cheese price as well as its plain price**, because both are part of that same scalable total. Getting this wrong made the advice under-deliver by ₱542 a night on a cheese-heavy fortnight; the test now SETS the advised prices, replays the identical mix and asserts the night really leaves the figure asked for.
- **A cost cell is a usable figure or it is blank.** `costCell` reads it: anything that is not a finite figure ≥ 0 (a typed "₱120", "12,50", "-5") reads exactly like blank — reported in `unpriced`, left out, shown empty so it gets retyped. Zero is an answer (nori's box costs nothing). Coercing junk to 0 was silently costing at nothing with every guard quiet.

UI: **More → "What it costs"**, Nayt's screen (Mama never needs it) — the per-ball stack, per-box margins, break-even, and the target table. `unit_cost` and `box_cost` are editable under Maintenance beside the figures they belong to.

Tab **StockItems** (product | unit | active | sort | **opening_qty** | **opening_date** | **reorder_at**) — `opening_qty`/`opening_date` are the one-time starting baseline; `reorder_at` is the low-stock threshold (0 or blank = no warning). A **blank** `reorder_at` ships blank (`''`), not 0: it is the one figure in this row read raw, because 0 is a legitimate threshold and a coerced blank comes straight back on the next `saveStockItems` and fills the owner's untouched cells with literal 0s.

**Seed all six items with `opening_qty` 0 and a blank `opening_date`** (owner's decision, 2026-08-01: he will set real figures via "Correct the count" after his first stocktake rather than typing them up front). A blank `opening_date` must mean *count the whole history* — comparisons are lexicographic on `yyyy-MM-dd` strings and `'' < any date`, so this falls out naturally, but it has to be deliberate rather than accidental: a blank baseline date must never be coerced to today, or every delivery already logged would be silently excluded. `reorder_at` seeds blank, and then the v2.7.0 backfill (item 1 above) immediately fills the three named products — Flour 5, Sauce 1, Mayo 1 — so a fresh sheet warns on those from day one; everything else stays blank (no warning) until the owner sets a threshold.

Because the seeded baseline is 0, on-hand can legitimately read **negative** before the first stocktake (usage logged against stock that was delivered before tracking began). Show it plainly rather than clamping to zero — a negative figure is honest information that a count is needed, and silently clamping would hide it.

Tab **StockCounts** (date | product | counted_qty | entry_id | updated_at) — a physical stocktake, which **becomes the new baseline**. This is what stops estimation drift accumulating forever: spoilage, breakage and miscounts are absorbed the next time something is counted, instead of skewing on-hand indefinitely.

On hand is **computed, never stored** (same principle as backlog balances):

```
baseline   = latest StockCounts row for the product (by date, then updated_at)
             else { date: opening_date, qty: opening_qty }
delivered  = Σ StockDeliveries.qty  ("Stock came in", v2.6.0 — the only door
             new arrivals use)
           + Σ Expenses.stock_qty   (LEGACY pre-2.6.0 rows, kept counting
             forever) — both for the product, date > baseline.date
used       = Σ StockUsage.qty       for the product, date > baseline.date
on_hand    = baseline.qty + delivered − used
low        = reorder_at > 0 && on_hand <= reorder_at
```

Deliveries and usage are counted **strictly after** the baseline date, so a stocktake is understood as an end-of-day figure that already reflects that day's activity. The UI must say so where a count is entered.

`bootstrap` returns each stock item with `on_hand`, `low`, `baseline_qty`, `baseline_date`, `delivered_since` and `used_since` so the phone can show the figure and explain it without recomputing history it doesn't have.

New action **`saveStockCount`** payload `{date, product, qty, entryId}` → upsert by `entry_id` into StockCounts. Returns `{entry_id, on_hand}`.

### v2.9.3 — the screen she reads, and the wait that used to have no end

Two things this release, both found by measuring rather than looking.

**The palette is now checked by arithmetic.** The design above is unchanged in intent, but two of its colours were doing a job they could not carry at the brightness this app is actually used at — outdoors, at night, on a phone left on low, by a woman in her sixties. Measured against WCAG: the hairline `--line` on `--bg` is **1.25:1** where a boundary that tells her which box a figure belongs to needs **3:1**, and `--accent` used as *text* is **4.04:1** where text needs **4.5:1**. So the palette gains exactly two tokens — `--line-strong` (#9C8465, 3.36:1) for the borders of `.card`, `.input`, `.chip`, `.step-btn`, `.step-val`, and `--accent-text` (#9C4A07, 5.83:1) for accent-coloured *text*. `--accent` itself is untouched wherever it **fills** (primary button, pressed chip) — white on it still passes. The selected tab, which said which screen she was on **in colour alone**, now also carries a 3px bar (`box-shadow:inset`). And the page finally **declares its scheme** (`<meta name="color-scheme" content="light">` plus `color-scheme:light`): without it, Android's forced-dark is free to invent its own inversion of a design that has one intended appearance, and money is what turns unreadable. Dark mode is still not required — declaring light is how we say so.

These ratios are **recomputed from the shipped file on every test run**, so the palette cannot quietly drift back.

**Nothing waits forever.** `fetch()` has no timeout of its own. A phone holding a socket open against a tower that has gone away — the ordinary way mobile data fails, mid-request, with no error — left the promise pending for as long as the OS allowed. The queue drains strictly in order, one item at a time, so that single pending promise froze the pill at *Syncing…* and blocked **every night behind it** until the app was closed and reopened, with nothing on screen to say so. Now every wire call goes through `fetchWithTimeout` (**30s** for the tracker, **75s** for the photo reader, which has to upload as well as read). The deadline is a **race**, not a callback on the abort signal: the abort is still sent so a cooperating platform drops the socket, but the caller is released whether the platform honours it or not — some old Android WebViews accept a signal and ignore it, and `AbortController` itself is guarded in case the constructor is missing.

Giving up early is safe here **because every queued action upserts on a key it carries** (a day by its date, everything else by `entry_id`/sku/product): a deadline that fires after the sheet was already written means the retry rewrites the same row rather than adding a second one. The message says so — *"did not answer within 30 seconds. Nothing is lost — it will try again."* — because a timed-out save may in fact have landed, and telling her it failed would be a lie.

Separately, `syncing` is now released in a **`finally`** rather than on the line after the loop. Every `api()` throw was already caught, but the catch itself runs code that can throw (`noteAttention`, `persistQueue` on a full localStorage, `toast`), and an escape from there left `syncing` stuck `true` — which makes `drainQueue` return at its own front door forever.

### v2.10.0 — "Does this night look right?": tonight judged against the other nights

Every other guard in this app judges tonight against **itself** — the arithmetic must hold, a start count needs an end count, a bucket cannot exceed what sold. None of them can see the failure that actually happened twice in one week: a figure that is perfectly self-consistent and simply **wrong**. nori read "nothing sold" for weeks (v2.9.8) with every internal check satisfied throughout; a ten-pack delivery logged as one (v2.9.6) passed every rule too. Neither was caught by the app — the owner caught them by eye.

So this compares tonight with the **nights before it**. It is the plain-language form of what stock systems call exception reporting, and the textbook signal is precisely the one that bit: *an item that normally sells, suddenly selling none, while the stock says it was there.*

**Three observations**, computed on the phone from history it already holds — no schema change, no new permission, no server call:
1. a sku with **no counts at all** tonight that is normally counted (reachable via a photo reading that returns a sku with neither figure read);
2. the **nori signature** — the shelf had stock and none of it moved, for a sku that sold on most recent nights;
3. the night's **take far outside** the usual: below `NIGHT_LOW_BAND` (0.4×) or above `NIGHT_HIGH_BAND` (2.5×) of the median of the last ten open nights.

**It is built to stay quiet**, because the one failure mode of this kind of feature is becoming noise nobody reads:
- it **never refuses and never changes a figure** — `Save day` is untouched, and the card says out loud that it is not a blocker;
- it says nothing until there are `NIGHT_MIN_HISTORY` (6) genuinely comparable nights — an opinion from thin history is a guess;
- **a blank is never evidence**: a night counts as comparable only when *both* of that sku's figures were entered;
- it appears **only once the night is otherwise savable**, so the specific complaint always speaks first and it cannot nag mid-entry;
- an **empty shelf is not an anomaly** (`sod > 0` is required), and a **closed night is never judged** — nor does a closed night drag the usual take down.

Every claim it makes is **auditable against her own paper** ("sold on 9 of the last 10 nights", "all 20 are still there"), because a warning she cannot check is a warning she has to take on faith.

### v2.12.1 — counting the tin

The other half of v2.12.0. The app can say what the tin **should** hold; this is the figure that says what it **really** held, so the two sit side by side before the money is collected.

New action **`saveTinCount`** `{start, end, counted, entryId}`. It lives on the **same `CutoffInputs` row as the split**, keyed on `(start, end)`, and writes only its own cell — `buildRow` starts from the existing row, so saving a count can never disturb a split already entered, or the reverse. The **local mirror had to be taught the same rule**: both appliers now merge instead of replacing, or saving one would have dropped the other on the phone while the sheet kept both. Centavos are kept, unlike the split: a tin holds coins, and rounding her count would manufacture the very difference this screen exists to find. A negative count is refused rather than clamped.

**Uncounted is `null`, never `0`.** `tin_counted` is carried RAW from the sheet, so "nobody has counted this cutoff" and "counted it and found nothing" stay distinguishable — coercing a blank to zero would report a shortage of the entire tin on every cutoff nobody got round to counting. A counted **zero** is a real answer and reads as a full shortage.

The verdict is one sentence with the peso figure, the direction, and where to look — *short*: "a wrong change given, a purchase nobody wrote down, or a count that slipped"; *over*: "usually a sale that never got written down, or a purchase entered twice". A shortage is shown in the alert colour. When unknown-source money exists in the cutoff, the verdict **says so and refuses to blame a difference it cannot account for**.

### v2.13.1 — catch up what was opened, from what is left on the shelf

Owner, 2026-08-28, after a fortnight nobody logged: he counted the tray — batter 2, mayo 1, sauce 1 — and *"with the remaining supplies, we should see the supplies cost for this cutoff."*

He was right to refuse a stocktake for this. A count **re-baselines**: the consumption it absorbs never reaches `StockUsage`, so the costing prices nothing and the supplies cost stays at zero. What the costing prices is what was logged as **opened**, so that is what has to be written.

The arithmetic is not a guess:

```
used = on_hand (baseline + delivered − logged usage) − what is really there now
```

**More → Stock on hand → "Catch up what was opened"** takes the count per product and shows, live, the units opened and the peso cost — his figures came to **₱2,600** — before anything is saved.

What it deliberately does **not** do:

- **It does not know which night each unit was opened on, and does not pretend to.** It fills ONE night's stock card, names that night on the button, and says plainly that *the cutoff total is right, the night-by-night is not.*
- **It saves nothing.** It fills the card, opens it, moves her to that night's Sales screen, and leaves the last word on `Save day` — where every other figure's last word is.
- **It adds to what that night already holds**, never replacing it: `saveDay` rewrites a night's whole usage block, so an existing figure has to survive.
- **A count HIGHER than expected is not negative usage** — it is a delivery nobody logged. Said as itself, pointed at "Stock came in", and left out of the total.
- **A product with no unit cost is counted but not costed**, and listed — the same rule the costing screen follows for an unpriced item.
- The night is chosen as the most recent open night **in the current cutoff** that logged nothing, falling back to tonight. It never reaches into an earlier cutoff: that fortnight has very likely been settled, and putting supplies into it would restate money that has already moved.

## API contract (Apps Script `doPost`)

Transport: `POST` with `Content-Type: text/plain;charset=utf-8` (avoids CORS preflight — Apps Script cannot answer OPTIONS), body = JSON `{token, action, payload}`. Response: `ContentService` JSON `{ok:true, data}` or `{ok:false, error}`. `doGet` returns `{ok:true, data:{name:"octogo-api", version}}` for connectivity tests (no token needed for doGet ping only).

**Key casing is deliberately asymmetric — do not "tidy" either side:**

- **Requests (client → server) are camelCase**: `cheeseQty`, `customAmount`, `entryId`, `backlogRef`, `stockProduct`, `stockQty`, `cheesePrice`, `reorderAt`, `dryRun`. This is what `doPost` parses; changing it breaks every queued mutation already sitting in a phone's `queue_v1`.
- **Responses (server → client) are snake_case**: `cheese_price`, `custom_amount`, `entry_id`, `updated_at`, `cheese_qty`, `regular_qty`, `backlog_ref`, `total_amount`, `start_date`, `per_partner`, `note_text`, `generated_at`, `counted_qty`, `split_amount`, `stock_product`, `stock_qty`, `on_hand`, `reorder_at`, `baseline_qty`, `baseline_date`, `delivered_since`, `used_since`. snake_case is canonical for stored/returned data because it matches the sheet's own column headers and the shape the PWA persists in `state_v1`. The only camelCase names a response may carry are the container keys `stockItems`, `stockUsage`, `stockCounts`, `stockDeliveries`, `cutoffInputs` and `lastCutoff`.

A response key that drifts to camelCase fails **silently**: the PWA reads `undefined` and renders it as 0 (this is exactly how the "cheese total is 0" bug shipped). The PWA's normalizers therefore read snake_case first and fall back to the legacy camelCase spelling, so a phone on new code talking to an older still-deployed Apps Script degrades safely instead of zeroing money. The cross-seam integration test is what keeps both ends honest.

Actions (all validate token first):
- `ping` → `{version}`
- `bootstrap` → `{settings, prices, stockItems, backlogs:[{...,paid,balance}], window_start, days, counts, stockUsage, stockCounts, stockDeliveries, expenses, cutoffInputs, lastCutoff}`
  **One 90-day date window for all six row collections** (days, counts, stockUsage, stockCounts, stockDeliveries, expenses) and `window_start` states it explicitly. Asymmetric windows were a bug: a row-capped `days` beside a 90-day `expenses` made an older cutoff preview show expenses with no sales behind them. And the phone needs the boundary stated, because inferring it from the dates present cannot tell "older than this reply covers" from "deleted in the sheet" — inside the window the snapshot is authoritative and a row it omits must be dropped locally; outside it the phone keeps its own history. Queued work is re-applied on top either way — **and so is the needs-attention list**, which is not optional: a mutation the server REFUSED leaves the queue (it would jam every later item) and lives only in `attention_v1`, so replaying the queue alone let the snapshot delete the one and only copy of a rejected day while the red card still told the user to go and fix it. The appliers are idempotent; the queue is replayed first and keeps the last word for any target it also carries.
  `stockItems` is **not** windowed and its ledger figures are computed over the WHOLE history (a delivery from six months ago is still on the shelf). `cutoffInputs` is period-keyed, not date-keyed: every row whose `end` falls inside the window ships, so the phone can pre-fill and preview the entered Split offline. `supplyItems` and `dailySupplies` are **gone** with the retired path.
- `saveDay` payload `{date, closed, staff, customAmount, customGcash, gcashConverted, lidBoxes, customBoxes:[{sku, qty}], salary, notes, counts:[{sku, sod, eod, cheeseQty, gcashQty, gcashCheeseQty}], stock:[{product, qty}], entryId}` — the three v2.7.0 keys are optional; absent means 0/none and the money computes exactly as before → server computes sold, the derived `regular_qty`, per-sku `amount` and `gcash_amount` from Prices (pricing `sold − custom_qty` per item 7), then `total`/`gcash`/`cash` per the roll-up above with `gcash_converted` inside `gcash`; upserts DailyLog by date and rewrites that date's DailyCounts and StockUsage. Returns computed `{total, cash, gcash, salary, excluded_total, gcash_converted, lid_boxes, dropped_skus, lines:[{sku, sold, cheese_qty, gcash_qty, gcash_cheese_qty, regular_qty, amount, gcash_amount, in_cutoff, custom_qty}]}`. Closed day: counts/stock empty, total 0, salary 0 and `excluded_total` 0 (stock is still cleared for that date).
  **An excluded sku (`in_cutoff=FALSE`) has no payment split at all**: a non-zero `gcashQty` on one is **refused**, naming the item and asking for a 0. Its money is out of `total`, so feeding its GCash into the day's `gcash` would break `Total = Cash + GCash`, and quietly keeping it inside `excluded_total` instead would leave the day's GCash figure silently short of the GCash app — which is the one thing that figure exists to be reconciled against. The Sales screen therefore shows no GCash stepper on an excluded sku.
  `salary` is optional: omit it (or send blank) and the server snapshots the current Settings `daily_salary`; send a figure for a half day; an explicit `0` is honoured. It is stored per day, never recomputed.
  Validation, each with a plain-English message: `sod`/`eod`/all quantities ≥ 0; `eod ≤ sod`; `cheeseQty + gcashQty + gcashCheeseQty ≤ sold`; `cheeseQty`/`gcashCheeseQty` = 0 for `group=simple`; `customGcash ≤ customAmount`; `salary` ≥ 0; stock quantities ≥ 0 **and whole numbers** (units opened). The StockItems list is advisory here — a renamed product must never make a day of sales un-saveable.
  **Note:** `gcash` is no longer accepted from the client — it is computed. Same for `supplies`, which a phone queued before the retirement still carries. Both are ignored rather than rejected, so old queued work cannot write a bogus figure or resurrect a dead tab.
- `saveExpense` payload `{date, category, item, amount, backlogRef, notes, entryId}` → upsert by entry_id; the upsert never touches a legacy row's `stock_product`/`stock_qty` cells. A payload carrying a NON-BLANK `stockProduct` or `stockQty` (an older phone's queued delivery) is **refused** with exactly: "Deliveries are recorded under Stock on hand now, so this expense should carry money only." — blank/absent stock keys are fine, every ordinary queued expense carries them as `''`. Returns `{entry_id, updated}`.
- `deleteExpense` payload `{entryId}` → remove row. Returns `{deleted}`.
- `saveStockCount` payload `{date, product, qty, entryId}` → upsert by entry_id into StockCounts. Returns `{entry_id, product, on_hand}` — `on_hand` **recomputed**, not echoed, so a backdated count lands on the arithmetic.
- `saveCutoffSplit` payload `{start, end, amount, entryId}` → upsert by (start, end). Returns `{entry_id, start, end, split_amount, per_partner}`.
- `savePrices` payload `{rows:[{sku, price, cheesePrice, active, inCutoff}]}` → upsert by sku; only those fields are written, and a sku the sheet does not have is **refused** (a price row also needs a group and a size, and guessing them would misprice cheese). A zero or blank `price` on a sku whose `active` is true is **refused too**, in a message naming the sku: ₱0 on a selling item silently books every future sale at nothing, and a cleared field arrives as 0. `cheesePrice` is a price by the same argument, so it is refused at 0 as well **when the sku's `group` is `box`** — a `group=simple` sku has no cheese version and must keep its 0. An **inactive** sku may keep a 0 — it sells nothing, and switching the sku off is how you stop selling it. The Maintenance screen enforces the identical rule inline (`priceRowError`) so the phone never queues a batch the server will refuse. `inCutoff` is **optional and only written when the payload explicitly carries it**: omitted (or blank) leaves that cell exactly as it is, blank included. Defaulting it would let one ordinary price save — or one batch queued by an older phone — switch every takoyaki sku out of the cutoff.
- `saveSettings` payload `{settings:{…}}` → whitelisted keys only (`branch`, `staff`, `daily_salary`, `split_default`, `mama_per_cutoff`, `electric_per_cutoff`, `supply_picklist`); **never `token`**; anything else is ignored. Returns `{saved:[keys], ignored:[keys]}`.
- `saveStockItems` payload `{rows:[{product, unit, reorderAt, active}]}` → upsert by product; `sort`, `opening_qty` and `opening_date` are never touched here. A product that does not exist yet IS created (it carries no money). Returns `{saved}`.
- `range` payload `{start, end}` → `{days, counts, stockUsage, stockCounts, expenses}` for the period (same row shapes as `bootstrap`).
**When the server refuses to make the note** (negative category, unsaved split), the phone must NOT offer its locally-built note as a fallback — the local copy would contain exactly the line the refusal exists to prevent. It shows the server's sentence and stops; demo/offline mode applies the same refusals locally before building anything.

**Stock on-hand on the phone (v2.5.1):** the server ships each product's delivered/used totals SPLIT at `window_start` (`delivered_before`, `used_before`); the phone adds its OWN local rows for dates inside the window. A local correction, deletion or closed day therefore moves on-hand immediately — the old "carry floor" (topping local figures back up to the server total) could not tell "rows I cannot see" from "rows I just corrected" and silently undid every downward fix.

**Excluded skus at the cutoff.** `figures` gains `excluded` (the period's total from `in_cutoff=FALSE` skus) and `excluded_lines` (`[{sku, label, qty, amount}]`). These are **display only**: they never enter `total`, `cash`, `gcash`, `supplies`, `remaining` or any other figure, and **the note text does not change at all** — the owner chose "Cutoff screen only" so what his partner receives is untouched. The Cutoff screen shows them as a clearly separate block below the note, labelled as not part of the cutoff.

**On the day's receipt** an excluded sku gets its own line *below* TOTAL/GCash/Cash — visible, never added in. This matters physically: nori cash sits in the same tin, so the tin equals `Cash + excluded_total`. The receipt must make that obvious or the tin will never appear to reconcile.

Show that block **only when there is excluded money that night** — a zero row and a tin line that restates Cash unchanged ("₱825 + ₱0 = ₱825") is noise on every ordinary night, and noise on the one screen used daily is a real cost. When there IS excluded money, the sticky day strip must show the tin figure too: the strip exists because the receipt is several screens down, so it is where the reconciliation actually gets read.

- `cutoff` payload `{start, end, dryRun}` → computes all note figures from DailyLog + Expenses + CutoffInputs in period; builds note_text in the exact format; if !dryRun upserts into Cutoffs by (start, end). Returns `{figures:{start, end, total, cash, gcash, mama, split, per_partner, supplies, octopus, salary, other, electric, remaining}, note_text}`. **`supplies` = Σ Expenses(category=Supplies) alone**; `split` is the entered amount for the period else Settings `split_default`, `per_partner = split / 2`; `salary` = Σ each day's salary over non-closed days (a blank counts at the current `daily_salary`); `remaining` is the residual and may be negative.

Row shapes returned by `bootstrap`/`range` mirror the sheet headers exactly: prices `{sku, label, group, size, price, cheese_price, active, in_cutoff}` — `in_cutoff` is the resolved boolean, so a blank or missing cell arrives as `true`; days `{date, closed, salary, staff, gcash, total, cash, custom_amount, custom_gcash, excluded_total, notes, entry_id, updated_at, gcash_converted, lid_boxes}` — `salary` is the EFFECTIVE figure (0 when closed, the day's snapshot, else the current rate), so the phone and the note can never disagree about it; `gcash_converted`/`lid_boxes` (v2.7.0) read 0 from a blank legacy cell; counts `{date, sku, sod, eod, sold, cheese_qty, regular_qty, amount, entry_id, gcash_qty, gcash_cheese_qty, gcash_amount, in_cutoff, price, cheese_price, custom_qty}` — `price`/`cheese_price` are the RESOLVED per-row snapshots (v2.5.0: the stored cell, else the sku's current price), so the phone shows a loaded day's arithmetic at the money it was saved at, and `custom_qty` (v2.7.0) is the special-order draw, 0 on a blank legacy cell; expenses `{date, category, item, amount, backlog_ref, notes, entry_id, updated_at, stock_product, stock_qty}` — the stock keys ship blank (`''`/0) on every post-2.6.0 row; stockUsage `{date, product, qty, entry_id, updated_at}`; stockCounts `{date, product, counted_qty, entry_id, updated_at}`; stockDeliveries `{date, product, qty, entry_id, updated_at}` (v2.6.0); cutoffInputs `{start, end, split_amount, entry_id, updated_at}`; stockItems `{product, unit, active, sort, opening_qty, opening_date, reorder_at, on_hand, low, baseline_qty, baseline_date, delivered_since, used_since, delivered_before, used_before}` — `delivered_before`/`used_before` are the pre-window parts split at `window_start` (v2.5.1, both delivery doors included); backlogs `{name, description, total_amount, start_date, active, paid, balance}`; lastCutoff `{start, end, total, cash, gcash, mama, split, per_partner, supplies, octopus, other, electric, note_text, generated_at}`.

Idempotency: every mutation carries client-generated `entryId` (uuid). Replaying the same saveDay/saveExpense/saveStockCount/saveCutoffSplit must not duplicate rows. Concurrency: use `LockService.getScriptLock()` around mutations.

Also in Code.gs: `setupSheet()` — run manually from the editor once; creates all tabs + headers + seed rows only if missing (idempotent), generates token, sets date columns to plain-text format, freezes header rows. `VERSION` constant. Script timezone must be set to Asia/Manila (note in file header: appsscript.json `"timeZone": "Asia/Manila"`).

## PWA

Files in `pwa/`: `index.html` (single-file app: all CSS/JS inline), `sw.js`, `manifest.webmanifest`, `logo.png` (header mark), `icon-192.png` / `icon-512.png` (home-screen icons, cropped from the Octogo Takoyaki Marikina logo — mascot on cream, padded so Android's maskable crop never clips the torii). That holds **even if the sheet says `group=box`** — a hand-edited row is rendered plain rather than showing cheese figures a save is about to refuse. `bentaPayload` and `computeDay` therefore treat all three of that row's buckets as `0`.
   `validateBenta` normally stays silent about a figure with no field to fix it (a cheese count on a `simple` sku is simply sent as 0), but a non-zero bucket on an EXCLUDED sku is the one exception: it can only exist because the sku used to count in the cutoff, or was hand-edited, so zeroing it silently would move money she has already read out of the day's GCash. It is **refused inline in the server's own words** — byte-identical to the message `saveDay` would return — and so is `in_cutoff=FALSE` on a `group=box` sku, which the Maintenance screen refuses to create for the same reason (`priceRowError`, mirroring `savePrices`).
   Live **receipt strip** (signature element): line items, then TOTAL / GCash / Cash (GCash directly under the total, since it is now computed and is the figure worth checking against GCash history); then, **below those and never inside them, and only on a night that has excluded money**, one line per excluded sku plus a single tin line ("Cash in the tin: ₱500 + ₱75 Nori = ₱575") — the excluded sku is kept out of the line items above too, so what is listed always adds up to TOTAL. `excludedTonight()` is the one rule for "is there excluded money tonight", read by the receipt AND the sticky strip so the two can never disagree; the strip adds one short "Tin ₱575" item beside Cash and GCash, and nothing at all when there is none. Save button = "Save day". Editing an already-saved day loads all of it back, including the stock card.
2. **Expenses** (panel id `gastos`): list grouped by date for current cutoff; add form (v2.7.1): ONE chip row [Octopus][…`supply_picklist`…][Other] + amount + date — no item box, no category chips; a named chip files as Supplies with that name as the item; Mama, Electric and backlog payments enter on the Cutoff screen. Categories remain the stored values, never translated, date defaults today. Tap to delete own entries.
3. **Cutoff**: period picker (defaults to current cutoff; prev/next arrows); live preview computed from local data: Total/Cash/GCash + expense category sums + Split (per partner); pre-fills Mama & Electric from settings as suggested expenses if none logged (one-tap "add ₱500"); **Generate cutoff note** → calls API `cutoff`, shows exact note text with **Copy** and **Share** (Web Share API) buttons. **Below the note block** (and below the Generate button when no note has been made yet) sits a dashed **"Not part of this cutoff"** card: one line per excluded sku (label × qty and its money) and a "Total kept out" line, with the copy saying plainly that this money is in none of the figures above and in none of the note. It is absent entirely when nothing excluded was sold. `computeCutoff` returns `excluded` / `excludedLines` for it — computed after the residual, read by nothing else, and `buildNote` never sees them.
4. **More** (panel id `ibapa`): backlogs with computed balances and a "Total remaining" line; sync status + pending queue count + "Sync now"; API setup (URL + token fields, "Test connection"); staff list comes from settings; version; link to open the Google Sheet.

Offline-first: service worker caches app shell (cache-first, versioned). All mutations go into a localStorage queue (`queue_v1`) with entryId; optimistic local state (`state_v1` mirror of bootstrap) updates immediately; background sync drains queue on `online`/`visibilitychange`/app start/after save; per-item retry, keep order; status pill: "Synced" (green) / "N waiting" (amber) / "Offline" (gray), matching the More screen's "Waiting to send" row. Demo mode: if no API URL configured, app is fully usable locally and banner says data is on this phone only until API is set up.

Resilience: `state_v1`/`queue_v1`/`config_v1` are always merged over complete defaults and element-wise sanitized on load, so a partial, truncated or non-JSON value can never blank the app; well-formed queued mutations always survive. **Data arriving from the API must go through the same sanitizers as data read from storage** — a malformed row in the sheet must never discard an otherwise-good bootstrap, and must never reach the DOM unescaped. Every render is wrapped so a thrown renderer shows a recovery message instead of an empty screen.

Error copy: never surface raw browser/network strings ("Failed to fetch") to the user — always translate to plain English with a next step.

API client: `fetch(url, {method:'POST', body: JSON.stringify(...)})` with **no custom headers** (text/plain default → no preflight), `redirect:'follow'`.

Number formatting: `toLocaleString('en-PH')`, ₱ sign in UI, none in note text. Peso amounts may have centavos; display without decimals when whole.

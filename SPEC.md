# Octogo Takoyaki — Daily Tracker (PWA + Google Apps Script + Google Sheets)

One system, three parts:
1. **Google Sheet** = database (free, owner-readable, no vendor lock-in).
2. **Apps Script Web App** = free JSON API bound to that sheet (deployed by owner, "execute as me", "anyone with link").
3. **PWA** = phone-installable app (static hosting), offline-first, syncs when online.

Users: **Mama** (daily entry at closing time), **Nayt** (dashboard + bi-monthly cutoff note).
Locale: Philippines. Timezone **Asia/Manila** everywhere. Currency PHP. Dates are plain strings `yyyy-MM-dd` end-to-end (never Date objects in sheet cells — write as strings with a leading `'` not needed if column formatted as plain text; Apps Script must set number format `@` on date columns).

## Business rules (verified against owner's real cutoff notes)

- Cutoff periods: **1–15** and **16–end of month**.
- Daily sales are computed from **container counts**: start-of-day (SOD) vs end-of-day (EOD) per box size. Sold = SOD − EOD. Sold then splits into four buckets — Cheese, GCash, GCash Cheese, and plain regular cash as the remainder (see the DailyCounts section).
- Current prices (seed data; editable in sheet `Prices` tab):
  - Octobits (regular): 4pcs ₱50, 6pcs ₱65, 10pcs ₱105
  - Chizubits (cheese): 4pcs ₱60, 6pcs ₱80, 10pcs ₱125
  - No drinks SKU (owner sells takoyaki only). To add one later, append a Prices row with `group=simple`.
- Custom orders: free peso amount + optional note per day.
- **GCash is computed**, not typed: it is the sum of the per-sku GCash buckets plus `custom_gcash`. **Cash = Total − GCash** still holds. The receipt displays the computed GCash so it can be reconciled against GCash history.
- **Split is an ENTERED amount, not the residual** (owner, 2026-08-03). Default `split_default` = ₱3,000 (₱1,500 each), editable per cutoff. `per_partner = split / 2`.
- Identity is therefore `Total = Cash + GCash` and `Total = Mama + Split + Supplies + Octopus + Salary + Other payments + Electric + Remaining`, where **Remaining is the residual** — what is left in the business after everything, and the figure backlog payments are funded from. Remaining may be negative (a short cutoff); show it, never clamp it.
- **Daily salary** ₱200 (`daily_salary`, Settings) is added automatically for every day NOT marked closed, snapshotted onto the day when it is saved so a later rate change never rewrites history. Editable per day for a half day. Subject to change once the owner finishes costing.
- **Mama** ₱500 per cutoff is her **share** (she is a third person — not the partner the Split is divided with) and **Electric bill** ₱500 are per-cutoff amounts logged as expenses, each offered as a one-tap chip on the Cutoff screen.
- **Octopus** is its own expense category (bulk purchase, paid per cutoff — kept separate from Supplies by owner's explicit request).
- **Backlog payments**: owner maintains a list of debts/obligations ("backlogs"), each with a total amount and running balance; he pays variable amounts per cutoff depending on excess. These payments + misc = the note's "Other payments" line.

### Cutoff note format (must match EXACTLY, including blank line placement; numbers use thousands separators, no ₱ sign, no decimals for whole numbers)

```
Tañong: July 1 - 15 Breakdown

Total - 11,857

Cash - 10,530
GCash - 1,327

Mama - 500
Split - 3,000(1,500 each)
Supplies - 5,440
Octopus - 
Salary - 3,000
Other payments - 1,417
Electric bill - 500

Short - 2,000
```

Rules, all load-bearing:
- When a category is zero, keep the line with a **blank value after "- "** — exactly as `Octopus - ` above (note the trailing space). Branch name from Settings.
- `Total`, `Cash` and `GCash` always print a number (`0` when empty); only the seven expense/share categories blank at zero.
- The final line is the residual and its LABEL carries the sign, so a note never reads `- -2,000`:
  `Remaining - 1,000` when ≥ 0, `Short - 2,000` when negative. It always prints a number.
- `Salary` was added 2026-08-03 and the residual line with it. The old ten-line note is no longer canonical; this is.

## Google Sheet schema (created by `setupSheet()` in Apps Script — flat tables, row 1 = headers, NO merged cells)

Tab **Settings** (key | value):
- `token` — API shared secret (random 32 chars, generated by setup)
- `branch` — "Tañong"
- `mama_per_cutoff` — 500
- `electric_per_cutoff` — 500
- `partners` — "Nayt, Partner" (display only)
- `staff` — "Mama" (comma-separated list for staff picker)
- `daily_salary` — 200 (added to every non-closed day; snapshotted per day at save)
- `split_default` — 3000 (pre-fills the Cutoff screen's editable Split)

Tab **Prices** (sku | label | group | size | price | cheese_price | active | **in_cutoff**):
- `box4` | Box 4 | box | 4 | 50 | 60 | TRUE | TRUE
- `box6` | Box 6 | box | 6 | 65 | 80 | TRUE | TRUE
- `box10` | Box 10 | box | 10 | 105 | 125 | TRUE | TRUE
- `nori` | Nori | simple | | 25 | | TRUE | **FALSE**

**`in_cutoff` = FALSE means "sell it, count it, but keep its money out of every cutoff figure"** (owner, 2026-08-04: nori is his own line of business — "it must not be added to the bi-monthly cutoff, just show the total per cutoff, and I'll exclude it on my own").

(`group=box` → SOD/EOD + cheese split; `group=simple` → SOD/EOD only, single price. Nori is `simple`: start/end counts, one price, no cheese and no GCash split.)

> **A BLANK `in_cutoff` MUST read TRUE.** After migration every existing Prices row has an empty cell in that column; if blank were read as FALSE, every takoyaki sku would silently drop out of the cutoff and the note would collapse to almost nothing. Blank = counts in. The same rule applies to an unrecognised value — anything that is not explicitly false-y counts in, because the failure mode of guessing wrong is deleting money from the note.

> **The flag is SNAPSHOTTED onto each DailyCounts row at save time**, exactly as prices are, and history is classified by that snapshot — never by the current Prices flag. Otherwise flipping "counts in the cutoff" in Maintenance silently restates money that was already saved, in both directions: a past ₱300 of nori would either vanish from the excluded block or reappear inside a total it was never part of. A BLANK snapshot on a count row reads TRUE (v2.5.0): a legacy row's money provably reached `total` when it was saved, so classifying it by the CURRENT flag double-stated migrated history the moment a sku was excluded. Blank = it counted.

> **An excluded sku must be `group=simple`.** Keeping money out of the cutoff means it is one plain quantity × one price — no cheese variant and no cash/GCash split. `savePrices` and `saveDay` both refuse `in_cutoff=FALSE` on a `group=box` sku, and refuse a non-zero cheese or GCash bucket on any excluded sku, naming the item in plain English. Without that rule the UI hides the cheese steppers while the payload still carries cheese quantities, so the phone and the sheet disagree about what was sold.

Tab **DailyLog** (date | closed | staff | gcash | total | cash | custom_amount | notes | entry_id | updated_at | **custom_gcash** | **salary** | **excluded_total**) — one row per date, upsert by date. `gcash` is now **computed** (see below), not typed. `custom_gcash` = how much of `custom_amount` was paid by GCash. `salary` = that day's wage, snapshotted from Settings at save time (0 on a closed day); a blank on a pre-existing non-closed row counts at the current `daily_salary`. `excluded_total` = that day's money from `in_cutoff=FALSE` skus, stored separately and **never** part of `total`, `cash` or `gcash`.

Tab **DailyCounts** (date | sku | sod | eod | sold | cheese_qty | regular_qty | amount | entry_id | **gcash_qty** | **gcash_cheese_qty** | **gcash_amount** | **in_cutoff**) — N rows per date, rewritten on day upsert, computed **server-side** (price snapshot).

**Four payment/variant buckets per sku** (mirrors the owner's own Sales Calculator: Cheese / GCash / GCash Cheese / Regular). They are mutually exclusive and must sum to `sold`:

| column | meaning | entered? |
| --- | --- | --- |
| `cheese_qty` | cheese, paid **cash** | yes |
| `gcash_qty` | regular, paid **GCash** | yes |
| `gcash_cheese_qty` | cheese, paid **GCash** | yes |
| `regular_qty` | regular, paid cash | **derived** = sold − the three above |

```
amount       = (regular_qty + gcash_qty) * price + (cheese_qty + gcash_cheese_qty) * cheese_price
gcash_amount = gcash_qty * price + gcash_cheese_qty * cheese_price
```

**Snapshots travel with the FIRST save too (v2.5.1).** A saveDay count may carry the `price`, `cheesePrice` and `inCutoff` the phone DISPLAYED when the night was entered; the server uses them for a sku's first row on that date, so a save queued offline lands at the money the receipt and the tin showed — never at whatever the prices happen to be when it finally syncs. On a RE-save, the stored per-date snapshots win (payload values fill only skus new to that date). Classification on re-save uses the stored `in_cutoff` snapshot for the same reason: a Maintenance flip must never move an already-saved day's money between the cutoff and the excluded block — the Sales screen, the Cutoff screen and the sheet must tell one story.

Day roll-up counts **only `in_cutoff` skus**: `total = Σ amount (in_cutoff only) + custom_amount`, `gcash = Σ gcash_amount (in_cutoff only) + custom_gcash`, `cash = total − gcash`, and `excluded_total = Σ amount (in_cutoff=FALSE)` kept entirely apart. So **Cash = Total − GCash still holds**, but GCash is now derived from what was actually entered instead of read off the GCash app. The receipt shows the computed GCash so it can still be reconciled against GCash history.

`group=simple` skus have no cheese: `cheese_qty` and `gcash_cheese_qty` must be 0; only `gcash_qty` splits payment.

Tabs **SupplyItems** / **DailySupplies** — **RETIRED 2026-08-03.** The owner judged the nightly "supplies bought today" card redundant with the Expenses tab, so the card is gone, `saveDay` no longer writes these tabs, and the cutoff no longer reads them: **`Supplies` on the note is now Expenses(category=Supplies) alone.** The tabs are left in place (never deleted — that is the migration rule) but are dead. Anything an early user typed there stops counting; there was no such data when this changed.

Tab **StockItems** (product | unit | active | sort) — the unit is the thing you OPEN, not a weight: Takoyaki Flour (pack), Takoyaki Sauce (gallon), Japanese Mayo (pack), Bonito (pack), Aonori (pack), Togarashi (pack).

Tab **StockUsage** (date | product | qty | entry_id | updated_at) — **whole units opened that day, counted like the boxes** (owner, 2026-08-03: "if a gallon of sauce is opened, it's considered used in that day"). Integers only — never fractional weights, never a running estimate. Only non-zero rows. **Never money**: it touches no total and no note line; it drives on-hand and the reorder warning.

### Stock on hand — deliveries, counts and the reorder warning

> **STATUS: being built now** (owner asked for it 2026-08-03: "Supplies section where i can see the current supplies count"). All quantities here are **whole units** — the thing you open — matching StockUsage.

A delivery has two faces: money paid, and quantity received. **Money stays in exactly one place — the `Expenses` row — and the quantity rides along on it.** So `Expenses` gains two appended columns:

Tab **Expenses** (… | **stock_product** | **stock_qty**) — optional. A delivery is an ordinary expense row (category `Supplies`, or `Octopus` for octopus so it lands on its own note line) that additionally names what arrived. `amount` is counted once as it always was; `stock_qty` feeds only the stock ledger. Leaving both blank is normal — most expenses aren't tracked stock.

Tab **StockItems** (product | unit | active | sort | **opening_qty** | **opening_date** | **reorder_at**) — `opening_qty`/`opening_date` are the one-time starting baseline; `reorder_at` is the low-stock threshold (0 or blank = no warning). A **blank** `reorder_at` ships blank (`''`), not 0: it is the one figure in this row read raw, because 0 is a legitimate threshold and a coerced blank comes straight back on the next `saveStockItems` and fills the owner's untouched cells with literal 0s.

**Seed all six items with `opening_qty` 0 and a blank `opening_date`** (owner's decision, 2026-08-01: he will set real figures via "Correct the count" after his first stocktake rather than typing them up front). A blank `opening_date` must mean *count the whole history* — comparisons are lexicographic on `yyyy-MM-dd` strings and `'' < any date`, so this falls out naturally, but it has to be deliberate rather than accidental: a blank baseline date must never be coerced to today, or every delivery already logged would be silently excluded. `reorder_at` seeds blank (no warning) until the owner sets thresholds in the sheet.

Because the seeded baseline is 0, on-hand can legitimately read **negative** before the first stocktake (usage logged against stock that was delivered before tracking began). Show it plainly rather than clamping to zero — a negative figure is honest information that a count is needed, and silently clamping would hide it.

Tab **StockCounts** (date | product | counted_qty | entry_id | updated_at) — a physical stocktake, which **becomes the new baseline**. This is what stops estimation drift accumulating forever: spoilage, breakage and miscounts are absorbed the next time something is counted, instead of skewing on-hand indefinitely.

On hand is **computed, never stored** (same principle as backlog balances):

```
baseline   = latest StockCounts row for the product (by date, then updated_at)
             else { date: opening_date, qty: opening_qty }
delivered  = Σ Expenses.stock_qty   for the product, date > baseline.date
used       = Σ StockUsage.qty       for the product, date > baseline.date
on_hand    = baseline.qty + delivered − used
low        = reorder_at > 0 && on_hand <= reorder_at
```

Deliveries and usage are counted **strictly after** the baseline date, so a stocktake is understood as an end-of-day figure that already reflects that day's activity. The UI must say so where a count is entered.

`bootstrap` returns each stock item with `on_hand`, `low`, `baseline_qty`, `baseline_date`, `delivered_since` and `used_since` so the phone can show the figure and explain it without recomputing history it doesn't have.

New action **`saveStockCount`** payload `{date, product, qty, entryId}` → upsert by `entry_id` into StockCounts. Returns `{entry_id, on_hand}`.

### Editable Split per cutoff

Tab **CutoffInputs** (start | end | split_amount | entry_id | updated_at) — upsert by (start, end). New action **`saveCutoffSplit`** payload `{start, end, amount, entryId}`. `apiCutoff` reads the row for the period and falls back to Settings `split_default`; `per_partner = split / 2`. The Cutoff screen shows Split as an editable amount pre-filled from whichever applies, and the residual (`Remaining`/`Short`) updates live as it is changed. Two rules keep that field honest, because the NOTE is built from the saved row and nothing else: an **empty** field means the default (`splitFieldAmount`), never ₱0 — otherwise the headline residual swings by the whole split and flips its label; and while the field differs from what is saved, **"Generate cutoff note" refuses** and says to save the split first (`pendingSplit`). A note that contradicts the figures printed directly above it is worse than no note.

### Maintenance screen (More → Maintenance)

One place to change the constants without opening the sheet on a phone (owner asked, 2026-08-03). Edits **Prices** (per sku: price, cheese price, active, and **"Counts in the cutoff"** — the `in_cutoff` flag, off for nori; the cheese-price field is shown only for `group=box`, because a `simple` sku has no cheese version and must keep its 0), **Settings** (`daily_salary`, `split_default`, `mama_per_cutoff`, `electric_per_cutoff`, `branch`, `staff`) and **StockItems** (`unit`, `reorder_at`, `active`).

New actions **`savePrices`** payload `{rows:[{sku, price, cheesePrice, active, inCutoff}]}` (see the API contract entry for the omitted-means-leave-alone rule), **`saveSettings`** payload `{settings:{…}}` (whitelisted keys only — **never** `token`), and **`saveStockItems`** payload `{rows:[{product, unit, reorderAt, active}]}`. All upsert by natural key, all under the script lock, all leaving unlisted rows and unknown keys untouched.

Price edits apply to **future days only** — historical DailyCounts keep their snapshotted amounts, which is the whole point of computing money at save time. The screen must say so plainly next to the price fields.

`saveExpense` payload gains optional `stockProduct` and `stockQty`; validation: a `stockQty` requires a `stockProduct` that exists in StockItems, and `stockQty` ≥ 0 **and a whole number** — you receive 2 gallons, never 1.5, and the quantity is added straight into on-hand. Same for `saveStockCount`'s `qty`: whole units, refused in the same words `saveDay` uses.

UI: the expense form shows an optional "What arrived?" (product + quantity) when the category is one that can carry stock; **More** gets a "Stock on hand" card listing each item with its unit, a low badge, and a "Correct the count" action; the Sales screen shows a single quiet line when anything is at or below its reorder point — never a modal, never blocking the day's entry.

> **Double-counting hazard, now closed by design:** a purchase belongs in exactly one place, and since the daily-supplies card was retired (2026-08-03) there *is* only one place — `Expenses` (category `Supplies`, or `Octopus`). Nothing else feeds the `Supplies` note line.

Consequently **all tab readers must map columns by header NAME, not by fixed index** — a sheet created before this change has 9 DailyCounts columns, one created after has 12, and both must read correctly.

Tab **Expenses** (date | category | item | amount | backlog_ref | notes | entry_id | updated_at | stock_product | stock_qty) — append/upsert by entry_id. Categories: `Supplies`, `Octopus`, `Electric`, `Mama`, `Backlog`, `Other`. The last two columns are the optional delivery quantity described above.

Salary and Remaining have no columns of their own: the archived `note_text` carries them, and both are recomputed from DailyLog + Expenses + CutoffInputs whenever the period is asked for again.

## API contract (Apps Script `doPost`)

Transport: `POST` with `Content-Type: text/plain;charset=utf-8` (avoids CORS preflight — Apps Script cannot answer OPTIONS), body = JSON `{token, action, payload}`. Response: `ContentService` JSON `{ok:true, data}` or `{ok:false, error}`. `doGet` returns `{ok:true, data:{name:"octogo-api", version}}` for connectivity tests (no token needed for doGet ping only).

**Key casing is deliberately asymmetric — do not "tidy" either side:**

- **Requests (client → server) are camelCase**: `cheeseQty`, `customAmount`, `entryId`, `backlogRef`, `stockProduct`, `stockQty`, `cheesePrice`, `reorderAt`, `dryRun`. This is what `doPost` parses; changing it breaks every queued mutation already sitting in a phone's `queue_v1`.
- **Responses (server → client) are snake_case**: `cheese_price`, `custom_amount`, `entry_id`, `updated_at`, `cheese_qty`, `regular_qty`, `backlog_ref`, `total_amount`, `start_date`, `per_partner`, `note_text`, `generated_at`, `counted_qty`, `split_amount`, `stock_product`, `stock_qty`, `on_hand`, `reorder_at`, `baseline_qty`, `baseline_date`, `delivered_since`, `used_since`. snake_case is canonical for stored/returned data because it matches the sheet's own column headers and the shape the PWA persists in `state_v1`. The only camelCase names a response may carry are the container keys `stockItems`, `stockUsage`, `stockCounts`, `cutoffInputs` and `lastCutoff`.

A response key that drifts to camelCase fails **silently**: the PWA reads `undefined` and renders it as 0 (this is exactly how the "cheese total is 0" bug shipped). The PWA's normalizers therefore read snake_case first and fall back to the legacy camelCase spelling, so a phone on new code talking to an older still-deployed Apps Script degrades safely instead of zeroing money. The cross-seam integration test is what keeps both ends honest.

Actions (all validate token first):
- `ping` → `{version}`
- `bootstrap` → `{settings, prices, stockItems, backlogs:[{...,paid,balance}], window_start, days, counts, stockUsage, stockCounts, expenses, cutoffInputs, lastCutoff}`
  **One 90-day date window for all five row collections** (days, counts, stockUsage, stockCounts, expenses) and `window_start` states it explicitly. Asymmetric windows were a bug: a row-capped `days` beside a 90-day `expenses` made an older cutoff preview show expenses with no sales behind them. And the phone needs the boundary stated, because inferring it from the dates present cannot tell "older than this reply covers" from "deleted in the sheet" — inside the window the snapshot is authoritative and a row it omits must be dropped locally; outside it the phone keeps its own history. Queued work is re-applied on top either way — **and so is the needs-attention list**, which is not optional: a mutation the server REFUSED leaves the queue (it would jam every later item) and lives only in `attention_v1`, so replaying the queue alone let the snapshot delete the one and only copy of a rejected day while the red card still told the user to go and fix it. The appliers are idempotent; the queue is replayed first and keeps the last word for any target it also carries.
  `stockItems` is **not** windowed and its ledger figures are computed over the WHOLE history (a delivery from six months ago is still on the shelf). `cutoffInputs` is period-keyed, not date-keyed: every row whose `end` falls inside the window ships, so the phone can pre-fill and preview the entered Split offline. `supplyItems` and `dailySupplies` are **gone** with the retired path.
- `saveDay` payload `{date, closed, staff, customAmount, customGcash, salary, notes, counts:[{sku, sod, eod, cheeseQty, gcashQty, gcashCheeseQty}], stock:[{product, qty}], entryId}` → server computes sold, the derived `regular_qty`, per-sku `amount` and `gcash_amount` from Prices, then `total`/`gcash`/`cash` per the roll-up above; upserts DailyLog by date and rewrites that date's DailyCounts and StockUsage. Returns computed `{total, cash, gcash, salary, excluded_total, dropped_skus, lines:[{sku, sold, cheese_qty, gcash_qty, gcash_cheese_qty, regular_qty, amount, gcash_amount, in_cutoff}]}`. Closed day: counts/stock empty, total 0, salary 0 and `excluded_total` 0 (stock is still cleared for that date).
  **An excluded sku (`in_cutoff=FALSE`) has no payment split at all**: a non-zero `gcashQty` on one is **refused**, naming the item and asking for a 0. Its money is out of `total`, so feeding its GCash into the day's `gcash` would break `Total = Cash + GCash`, and quietly keeping it inside `excluded_total` instead would leave the day's GCash figure silently short of the GCash app — which is the one thing that figure exists to be reconciled against. The Sales screen therefore shows no GCash stepper on an excluded sku.
  `salary` is optional: omit it (or send blank) and the server snapshots the current Settings `daily_salary`; send a figure for a half day; an explicit `0` is honoured. It is stored per day, never recomputed.
  Validation, each with a plain-English message: `sod`/`eod`/all quantities ≥ 0; `eod ≤ sod`; `cheeseQty + gcashQty + gcashCheeseQty ≤ sold`; `cheeseQty`/`gcashCheeseQty` = 0 for `group=simple`; `customGcash ≤ customAmount`; `salary` ≥ 0; stock quantities ≥ 0 **and whole numbers** (units opened). The StockItems list is advisory here — a renamed product must never make a day of sales un-saveable.
  **Note:** `gcash` is no longer accepted from the client — it is computed. Same for `supplies`, which a phone queued before the retirement still carries. Both are ignored rather than rejected, so old queued work cannot write a bogus figure or resurrect a dead tab.
- `saveExpense` payload `{date, category, item, amount, backlogRef, notes, stockProduct, stockQty, entryId}` → upsert by entry_id. Returns `{entry_id, updated}`.
- `deleteExpense` payload `{entryId}` → remove row. Returns `{deleted}`.
- `saveStockCount` payload `{date, product, qty, entryId}` → upsert by entry_id into StockCounts. Returns `{entry_id, product, on_hand}` — `on_hand` **recomputed**, not echoed, so a backdated count lands on the arithmetic.
- `saveCutoffSplit` payload `{start, end, amount, entryId}` → upsert by (start, end). Returns `{entry_id, start, end, split_amount, per_partner}`.
- `savePrices` payload `{rows:[{sku, price, cheesePrice, active, inCutoff}]}` → upsert by sku; only those fields are written, and a sku the sheet does not have is **refused** (a price row also needs a group and a size, and guessing them would misprice cheese). A zero or blank `price` on a sku whose `active` is true is **refused too**, in a message naming the sku: ₱0 on a selling item silently books every future sale at nothing, and a cleared field arrives as 0. `cheesePrice` is a price by the same argument, so it is refused at 0 as well **when the sku's `group` is `box`** — a `group=simple` sku has no cheese version and must keep its 0. An **inactive** sku may keep a 0 — it sells nothing, and switching the sku off is how you stop selling it. The Maintenance screen enforces the identical rule inline (`priceRowError`) so the phone never queues a batch the server will refuse. `inCutoff` is **optional and only written when the payload explicitly carries it**: omitted (or blank) leaves that cell exactly as it is, blank included. Defaulting it would let one ordinary price save — or one batch queued by an older phone — switch every takoyaki sku out of the cutoff.
- `saveSettings` payload `{settings:{…}}` → whitelisted keys only (`branch`, `staff`, `daily_salary`, `split_default`, `mama_per_cutoff`, `electric_per_cutoff`); **never `token`**; anything else is ignored. Returns `{saved:[keys], ignored:[keys]}`.
- `saveStockItems` payload `{rows:[{product, unit, reorderAt, active}]}` → upsert by product; `sort`, `opening_qty` and `opening_date` are never touched here. A product that does not exist yet IS created (it carries no money). Returns `{saved}`.
- `range` payload `{start, end}` → `{days, counts, stockUsage, stockCounts, expenses}` for the period (same row shapes as `bootstrap`).
**When the server refuses to make the note** (negative category, unsaved split), the phone must NOT offer its locally-built note as a fallback — the local copy would contain exactly the line the refusal exists to prevent. It shows the server's sentence and stops; demo/offline mode applies the same refusals locally before building anything.

**Stock on-hand on the phone (v2.5.1):** the server ships each product's delivered/used totals SPLIT at `window_start` (`delivered_before`, `used_before`); the phone adds its OWN local rows for dates inside the window. A local correction, deletion or closed day therefore moves on-hand immediately — the old "carry floor" (topping local figures back up to the server total) could not tell "rows I cannot see" from "rows I just corrected" and silently undid every downward fix.

**Excluded skus at the cutoff.** `figures` gains `excluded` (the period's total from `in_cutoff=FALSE` skus) and `excluded_lines` (`[{sku, label, qty, amount}]`). These are **display only**: they never enter `total`, `cash`, `gcash`, `supplies`, `remaining` or any other figure, and **the note text does not change at all** — the owner chose "Cutoff screen only" so what his partner receives is untouched. The Cutoff screen shows them as a clearly separate block below the note, labelled as not part of the cutoff.

**On the day's receipt** an excluded sku gets its own line *below* TOTAL/GCash/Cash — visible, never added in. This matters physically: nori cash sits in the same tin, so the tin equals `Cash + excluded_total`. The receipt must make that obvious or the tin will never appear to reconcile.

Show that block **only when there is excluded money that night** — a zero row and a tin line that restates Cash unchanged ("₱825 + ₱0 = ₱825") is noise on every ordinary night, and noise on the one screen used daily is a real cost. When there IS excluded money, the sticky day strip must show the tin figure too: the strip exists because the receipt is several screens down, so it is where the reconciliation actually gets read.

- `cutoff` payload `{start, end, dryRun}` → computes all note figures from DailyLog + Expenses + CutoffInputs in period; builds note_text in the exact format; if !dryRun upserts into Cutoffs by (start, end). Returns `{figures:{start, end, total, cash, gcash, mama, split, per_partner, supplies, octopus, salary, other, electric, remaining}, note_text}`. **`supplies` = Σ Expenses(category=Supplies) alone**; `split` is the entered amount for the period else Settings `split_default`, `per_partner = split / 2`; `salary` = Σ each day's salary over non-closed days (a blank counts at the current `daily_salary`); `remaining` is the residual and may be negative.

Row shapes returned by `bootstrap`/`range` mirror the sheet headers exactly: prices `{sku, label, group, size, price, cheese_price, active, in_cutoff}` — `in_cutoff` is the resolved boolean, so a blank or missing cell arrives as `true`; days `{date, closed, salary, staff, gcash, total, cash, custom_amount, custom_gcash, excluded_total, notes, entry_id, updated_at}` — `salary` is the EFFECTIVE figure (0 when closed, the day's snapshot, else the current rate), so the phone and the note can never disagree about it; counts `{date, sku, sod, eod, sold, cheese_qty, regular_qty, amount, entry_id, gcash_qty, gcash_cheese_qty, gcash_amount, in_cutoff}`; expenses `{date, category, item, amount, backlog_ref, notes, entry_id, updated_at, stock_product, stock_qty}`; stockUsage `{date, product, qty, entry_id, updated_at}`; stockCounts `{date, product, counted_qty, entry_id, updated_at}`; cutoffInputs `{start, end, split_amount, entry_id, updated_at}`; stockItems `{product, unit, active, sort, opening_qty, opening_date, reorder_at, on_hand, low, baseline_qty, baseline_date, delivered_since, used_since}`; backlogs `{name, description, total_amount, start_date, active, paid, balance}`; lastCutoff `{start, end, total, cash, gcash, mama, split, per_partner, supplies, octopus, other, electric, note_text, generated_at}`.

Idempotency: every mutation carries client-generated `entryId` (uuid). Replaying the same saveDay/saveExpense/saveStockCount/saveCutoffSplit must not duplicate rows. Concurrency: use `LockService.getScriptLock()` around mutations.

Also in Code.gs: `setupSheet()` — run manually from the editor once; creates all tabs + headers + seed rows only if missing (idempotent), generates token, sets date columns to plain-text format, freezes header rows. `VERSION` constant. Script timezone must be set to Asia/Manila (note in file header: appsscript.json `"timeZone": "Asia/Manila"`).

## PWA

Files in `pwa/`: `index.html` (single-file app: all CSS/JS inline), `sw.js`, `manifest.webmanifest`, `logo.png` (header mark), `icon-192.png` / `icon-512.png` (home-screen icons, cropped from the Octogo Takoyaki Marikina logo — mascot on cream, padded so Android's maskable crop never clips the torii). No frameworks, no build step, vanilla JS. Works on Android Chrome + iOS Safari (Add to Home Screen).

Self-updating: on `controllerchange` from a new service worker the app reloads itself so a published update lands on the FIRST open, not the second — but it holds the reload while the day is half-entered (`benta.dirty`) or a request is in flight, applying it after the save or on next open. It must never block on a non-empty queue (queued work is persisted and replays after reload; blocking there would strand demo-mode or offline phones on an old build forever).

Screens (bottom tab bar, thumb-reach). Internal ids stay `benta`/`gastos`/`ibapa` (renaming them would break saved data); the visible labels are English:
1. **Sales** (daily entry, default; panel id `benta`): date header (default today, tappable to backfill); "Closed today" toggle; staff chips; then per active box sku a count row: start-of-day stepper, end-of-day stepper, computed "Sold", and **three bucket steppers — Cheese, GCash, GCash Cheese** — with the remainder shown as plain-cash regular. Each row spells out its own arithmetic ("6 regular × ₱50 + 2 cheese × ₱60 + 2 GCash × ₱50 = ₱620") so a stepper never looks like it did nothing. Then custom order amount **+ how much of it was GCash** + note. **No typed GCash total** — it is computed and shown on the receipt for reconciling against GCash history.
   Below that, **two collapsible cards**, both saved with the same "Save day" action. The nightly screen is already ~4.5 phone-screens tall with "Save day" at the bottom, so a card that is right almost every night starts CLOSED — with its figure in the card's head, so it can be read without opening anything. A card holding a non-default or non-empty value starts OPEN: nothing already entered is ever hidden, and a validation error inside a closed card opens it before scrolling to the message.
   - **Wage for this day** — the day's salary, pre-filled from Settings `daily_salary` and snapshotted on save. Closed when it is simply the usual rate; open for a half day or a day nobody was paid (0 is a figure, not "empty").
   - **Stock used today** — StockItems with a **whole number of units opened** each, and its unit ("2 packs", "1 gallon"). Explicitly labelled as not money. Closed when nothing was opened. The unit is free text from Maintenance, so the row's own line is plain text escaped exactly ONCE (`stockRowSaid`) — escaping it twice printed the entity itself.
   (The old **Supplies bought today** card is RETIRED — see the DailySupplies note above. Purchases go under Expenses, which is now the only place they can be.)
   An **excluded sku** (`in_cutoff=FALSE`, i.e. nori) renders as a plain quantity card — start/end counts, computed Sold, ONE price, its own money line — marked with one short badge ("Not in the cutoff") and one short line ("You settle this money yourself."). It has **no bucket steppers at all** and no cheese price on it: no cheese and no GCash, because an excluded sku has no variant and no payment split, and the server refuses every one of the three. That holds **even if the sheet says `group=box`** — a hand-edited row is rendered plain rather than showing cheese figures a save is about to refuse. `bentaPayload` and `computeDay` therefore treat all three of that row's buckets as `0`.
   `validateBenta` normally stays silent about a figure with no field to fix it (a cheese count on a `simple` sku is simply sent as 0), but a non-zero bucket on an EXCLUDED sku is the one exception: it can only exist because the sku used to count in the cutoff, or was hand-edited, so zeroing it silently would move money she has already read out of the day's GCash. It is **refused inline in the server's own words** — byte-identical to the message `saveDay` would return — and so is `in_cutoff=FALSE` on a `group=box` sku, which the Maintenance screen refuses to create for the same reason (`priceRowError`, mirroring `savePrices`).
   Live **receipt strip** (signature element): line items, then TOTAL / GCash / Cash (GCash directly under the total, since it is now computed and is the figure worth checking against GCash history); then, **below those and never inside them, and only on a night that has excluded money**, one line per excluded sku plus a single tin line ("Cash in the tin: ₱500 + ₱75 Nori = ₱575") — the excluded sku is kept out of the line items above too, so what is listed always adds up to TOTAL. `excludedTonight()` is the one rule for "is there excluded money tonight", read by the receipt AND the sticky strip so the two can never disagree; the strip adds one short "Tin ₱575" item beside Cash and GCash, and nothing at all when there is none. Save button = "Save day". Editing an already-saved day loads all of it back, including the stock card.
2. **Expenses** (panel id `gastos`): list grouped by date for current cutoff; add form: category chips (Supplies / Octopus / Electric / Mama / Backlog / Other — these are stored values, never translated), item, amount, backlog picker when category=Backlog (shows balances), date defaults today. Tap to delete own entries.
3. **Cutoff**: period picker (defaults to current cutoff; prev/next arrows); live preview computed from local data: Total/Cash/GCash + expense category sums + Split (per partner); pre-fills Mama & Electric from settings as suggested expenses if none logged (one-tap "add ₱500"); **Generate cutoff note** → calls API `cutoff`, shows exact note text with **Copy** and **Share** (Web Share API) buttons. **Below the note block** (and below the Generate button when no note has been made yet) sits a dashed **"Not part of this cutoff"** card: one line per excluded sku (label × qty and its money) and a "Total kept out" line, with the copy saying plainly that this money is in none of the figures above and in none of the note. It is absent entirely when nothing excluded was sold. `computeCutoff` returns `excluded` / `excludedLines` for it — computed after the residual, read by nothing else, and `buildNote` never sees them.
4. **More** (panel id `ibapa`): backlogs with computed balances and a "Total remaining" line; sync status + pending queue count + "Sync now"; API setup (URL + token fields, "Test connection"); staff list comes from settings; version; link to open the Google Sheet.

Offline-first: service worker caches app shell (cache-first, versioned). All mutations go into a localStorage queue (`queue_v1`) with entryId; optimistic local state (`state_v1` mirror of bootstrap) updates immediately; background sync drains queue on `online`/`visibilitychange`/app start/after save; per-item retry, keep order; status pill: "Synced" (green) / "N waiting" (amber) / "Offline" (gray), matching the More screen's "Waiting to send" row. Demo mode: if no API URL configured, app is fully usable locally and banner says data is on this phone only until API is set up.

Resilience: `state_v1`/`queue_v1`/`config_v1` are always merged over complete defaults and element-wise sanitized on load, so a partial, truncated or non-JSON value can never blank the app; well-formed queued mutations always survive. **Data arriving from the API must go through the same sanitizers as data read from storage** — a malformed row in the sheet must never discard an otherwise-good bootstrap, and must never reach the DOM unescaped. Every render is wrapped so a thrown renderer shows a recovery message instead of an empty screen.

Error copy: never surface raw browser/network strings ("Failed to fetch") to the user — always translate to plain English with a next step.

API client: `fetch(url, {method:'POST', body: JSON.stringify(...)})` with **no custom headers** (text/plain default → no preflight), `redirect:'follow'`.

Number formatting: `toLocaleString('en-PH')`, ₱ sign in UI, none in note text. Peso amounts may have centavos; display without decimals when whole.

### Design direction (from design pass — follow exactly)

- Palette: rice-paper bg `#FBF8F2`; soy ink `#2B1D12`; takoyaki-sauce accent `#C25E0A` (primary actions); deep sear `#8F3D0C` (pressed/depth); nori `#3E5C3A` (success/synced); GCash functional blue `#1B6DE0` (GCash amounts only); alert `#B3402E`. Dark mode not required for MVP.
- Type: display/numerals **"Baloo 2"** (Google Fonts, SW runtime-cached, fallback `system-ui` rounded stack) — totals, tab labels, headings; body: `system-ui, -apple-system, "Segoe UI", Roboto`. Big type: day TOTAL is the largest thing on screen.
- Signature: the **receipt strip** — perforated bottom edge (CSS zigzag), tabular numerals, prints line items as they're entered; on save, a brief tear-off animation (respect `prefers-reduced-motion`).
- Everything else quiet and disciplined: generous spacing, 48px+ touch targets, steppers with giant +/− buttons (mama-friendly), visible focus rings, sentence case.
- **Interface language: English** (owner's request, 2026-07-31 — the app was originally built in Taglish and converted). Keep it simple, warm and unambiguous: short concrete words, active voice, no jargon. Proper nouns stay as-is (Octogo, Tañong, Octobits, Chizubits, GCash, Mama). Display dates render via `en-PH`, timezone always Asia/Manila. The generated cutoff note was always English and is unaffected.
- No hero sections, no marketing copy — this is a tool. Empty states instruct ("No expenses yet this cutoff. Tap + to add one.").
